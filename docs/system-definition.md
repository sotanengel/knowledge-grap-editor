## 1. 目的とスコープ

### 1.1 目的

非エンジニアを含む利用者が、ローカル環境のブラウザ上で**オントロジー（スキーマ／TBox）とナレッジグラフ（インスタンス／ABox）を直感的に作成・編集**し、その成果物を **MCP（Model Context Protocol）経由で AI エージェントが知識源として参照**できる状態にすることを目的とする。

### 1.2 設計原則

| # | 原則 | 意味 |
|---|---|---|
| P1 | **標準準拠、UI で隠蔽** | 内部は W3C 標準（RDF/OWL/SHACL/SPARQL）。ただし利用者に IRI・プレフィクス・構文を意識させない。 |
| P2 | **単一コンテナ・単一コマンド起動** | `docker run` 一発で UI・API・ストア・MCP がすべて立つ。外部 DB 不要。 |
| P3 | **ファイルが正（Portable）** | データはボリューム内の RDF ファイル＋ストアとして完結。エクスポートすれば他ツールでそのまま使える。ロックインしない。 |
| P4 | **AI は読み取り専用** | MCP は参照系ツールのみを公開する。書き込み・提案の仕組みは実装しない。KG の内容に責任を持つのは常に人間。 |
| P5 | **小さく作る** | MVP は「点と線を描いて Turtle で出せる／SPARQL で引ける／MCP で読める」まで。 |

### 1.3 スコープ外（初版）

- マルチテナント、SaaS 提供、課金
- 大規模分散クラスタ（10億トリプル級）
- 自然言語からの全自動オントロジー生成（AI は支援に留める）
- リアルタイム共同編集・複数ユーザー管理（個人利用のため不要）
- AI による KG への書き込み・変更提案（MCP は参照専用）
- OWL DL 相当の完全推論（§10.1 参照。ルールベースで機械的に導ける範囲に限定）

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| オントロジー（TBox） | クラス・プロパティ・階層・制約などの語彙定義 |
| ナレッジグラフ（ABox） | 上記語彙に従う具体的な事実（インスタンスとその関係）の集合 |
| トリプル | 主語・述語・目的語の 3 つ組。RDF の最小単位 |
| 名前付きグラフ | トリプル集合に IRI を付けて区画化したもの（Quad の第 4 要素） |
| CBD | Concise Bounded Description。あるノードを中心とした最小限の記述部分グラフ |
| MCP | Model Context Protocol。AI クライアントに外部ツール／リソースを公開する規格 |

### 3.1 機能要求（FR）

| ID | 要求 | 優先度 |

| FR-15 | MCP サーバー経由で AI が検索・近傍取得・SPARQL 実行できる（**参照のみ**） | 必須 |

### 3.2 非機能要求（NFR）

| ID | 分類 | 要求 |
|---|---|---|
| NFR-01 | 可搬性 | Linux / macOS / Windows（Docker Desktop）で同一イメージが動作。amd64 / arm64 両対応 |
| NFR-02 | 起動性 | `docker run` から 10 秒以内に UI 到達可能 |
| NFR-03 | 規模 | 単一ノードで 1,000 万トリプルまで実用的に動作（想定は 10 万〜100 万） |
| NFR-04 | 応答性 | 1,000 ノード規模のグラフ描画で 60fps 相当の操作感。SPARQL 単純クエリ 200ms 以内 |
| NFR-05 | 永続性 | すべての状態はマウントされた単一ボリューム配下に保存。コンテナ破棄で失われない |
| NFR-06 | 依存性 | 実行時に外部ネットワーク接続を必須としない（語彙定義は同梱） |
| NFR-07 | ブラウザ | Chrome / Edge / Firefox / Safari の最新 2 バージョン |
| NFR-08 | 監査性 | すべての変更が追記型ログに記録され、任意時点へ復元できる |

## 4. データ形式の選定

> ご相談いただいた「RDF でよいか」への回答。**結論：RDF を採用する。ただし RDF-star を前提とし、LPG 的な使い勝手は UI 層で吸収する。**

### 4.1 候補比較

| 観点 | RDF + OWL/SHACL | LPG（Neo4j / Cypher） | TypeDB | 独自 JSON スキーマ |
|---|---|---|---|---|
| 標準化 | ◎ W3C 勧告 | △ ISO GQL 策定中 | △ 独自 | × |
| 既存語彙の再利用 | ◎ schema.org 等が即使える | × 都度自作 | × | × |
| 推論 | ◎ RDFS / OWL 2 | △ 手続き的に自作 | ◎ 独自ルール | × |
| 制約検証 | ◎ SHACL | △ 部分的 | ◎ | △ |
| エッジへの属性付与 | △ → **RDF-star で ◎** | ◎ 得意 | ◎ | ◎ |
| クエリ表現力 | ◎ SPARQL 1.1 | ◎ Cypher | ◎ | × |
| LLM の可読性 | ◎ Turtle は簡潔で読みやすい | ○ | △ 学習例が少ない | △ |
| エコシステム | ◎ 変換・可視化・公開 KG が豊富 | ◎ ただし閉じがち | △ | × |

### 4.2 決定事項

- **正の形式：RDF 1.2（RDF-star）／シリアライズは Turtle・TriG**
  - 人間にも LLM にも読める。差分がテキストで取れるので Git 管理と相性が良い。
- **エッジのメタデータ（出典・確信度・有効期間）：RDF-star の quoted triple で表現**
  - 従来の Reification による 4 トリプル展開を避け、LPG 的な直感性を保つ。
- **API の交換形式：JSON-LD 1.1**
  - フロントエンド／外部連携ではただの JSON として扱え、必要なら `@context` で RDF に戻せる。
- **制約：SHACL**、**推論：OWL 2 RL**（実用的な表現力と計算量のバランス）
- **エクスポート互換：GraphML / CSV（ノード・エッジ表）も出力可能に**
  - Neo4j や Gephi へ持ち出したい場合の逃げ道を用意（P3）。

### 4.3 RDF を採用しても「難しくならない」ための工夫

| RDF の難所 | 本システムでの対処 |
|---|---|
| IRI を考えるのが面倒 | 利用者はラベルだけ入力。IRI はベース IRI + ULID で自動採番 |
| プレフィクス宣言 | 主要語彙のプレフィクスをプリセット。UI には表示名のみ出す |
| リテラルの型指定 | 入力値から型を推定し、インスペクタでプルダウン確認するだけ |
| 空白ノード | UI からは生成させない。インポート時は skolemize して IRI 化 |
| どの語彙を使うべきか | パレットに推奨語彙をキュレーションして提示（schema.org 優先） |

| レイヤ | 技術 | 選定理由 |

| フロントエンド | React 18 + TypeScript + Vite | 標準的。ビルド成果物は静的ファイルのみ |

| 検証 | pySHACL | SHACL Core / SPARQL 制約に対応 |
| 推論 | owlrl（RDFS / OWL 2 RL） | 実装が枯れており、materialization 方式で SPARQL と併用しやすい。外部推論器（HermiT/ELK）は不要 |

| MCP | MCP Python SDK | stdio / Streamable HTTP 両対応 |
| コンテナ | マルチステージ Dockerfile（python:3.12-slim ベース） | 目標イメージサイズ 400MB 以下 |

> **代替案**：チームの主言語が TypeScript の場合、バックエンドを Node.js + Fastify + `oxigraph` (WASM/napi) + `rdf-validate-shacl` に置き換え、フロントと言語を統一する構成も成立する。§15 Q7 で確認したい。

## 6. データモデル

### 6.1 名前付きグラフ構成

編集対象・生成物・検証定義を混ぜないため、以下の名前付きグラフに分離する。

| グラフ IRI | 内容 | 編集主体 |
|---|---|---|
| `urn:ontoforge:ontology` | クラス・プロパティ定義（TBox） | 利用者 |
| `urn:ontoforge:data` | インスタンスと事実（ABox） | 利用者 |
| `urn:ontoforge:shapes` | SHACL シェイプ | 利用者 |
| `urn:ontoforge:inferred` | 推論で導出されたトリプル | システム（再生成可能・エクスポート時は任意） |
| `urn:ontoforge:vocab/<name>` | 取り込んだ外部語彙（読み取り専用） | システム |
| `urn:ontoforge:layout` | ノード座標などの表示情報（RDF 本体を汚さない） | UI |

### 6.2 IRI 設計

```
ベース IRI（設定可能。既定: https://example.org/kg/）

  オントロジー用語  {base}ont#Person        ← パスカルケース（クラス）
                   {base}ont#worksFor      ← キャメルケース（プロパティ）
  インスタンス      {base}id/01J8Z3K5...    ← ULID で自動採番
  名前付きグラフ    urn:ontoforge:*
```

- インスタンス IRI は**不変**。表示名の変更は `rdfs:label` / `skos:prefLabel` の更新であり IRI は動かさない。
- オントロジー用語はラベルから slug 化した可読 IRI を初期値とし、公開前にリネーム可能（参照は一括更新）。

### 6.3 エッジ属性（RDF-star）

```turtle
:alice :worksFor :acme .

<< :alice :worksFor :acme >>
    prov:wasDerivedFrom <https://example.com/source/123> ;
    ontf:confidence 0.85 ;
    ontf:assertedAt "2026-08-20T09:00:00Z"^^xsd:dateTime ;
    ontf:assertedBy :user/taro .
```

AI は書き込みを行わないため、この仕組みの主用途は**インポートしたデータの出典管理**と、手入力時の確信度メモである。MVP には必須でないため Phase 2 で導入し、Phase 1 では通常のトリプルのみを扱う。

### 6.4 変更履歴

- 全ての書き込みを **RDF Patch 形式**（`A`／`D` 行）で `changelog/` に追記。
- 1 操作 = 1 パッチ = Undo/Redo の 1 単位。
- N 操作ごと、または時刻ベースで `snapshots/*.trig` を出力。復元は「直近スナップショット + 以降のパッチ再適用」。
- パッチには `actor`（`user` / `import:<file>` / `reasoner`）を記録する。MCP は書き込まないため、ここに AI 由来のエントリは現れない。

## 7. UI 設計

### 7.1 画面レイアウト

```
┌─ ヘッダ：プロジェクト切替 │ 検索 │ 推論実行 │ 検証 │ エクスポート ─────────┐
├──────────────┬──────────────────────────────────┬────────────────────┤
│              │                                  │                    │
│  左：語彙     │      中央：グラフキャンバス         │  右：インスペクタ    │
│              │                                  │                    │
│  ▸ クラス     │      ○ 田中太郎                  │  タイプ: 人物        │
│    ▸ 人物     │        │ 所属                    │  ラベル: [田中太郎]  │
│      ▸ 社員   │        ▼                         │  ─────────────      │
│    ▸ 組織     │      ○ 株式会社アクメ              │  生年月日: [ ]       │
│  ▸ プロパティ  │                                  │  メール:   [ ]       │
│    ・所属      │                                  │  ─────────────      │
│    ・設立年    │                                  │  関係                │
│  ▸ 外部語彙   │                                  │  所属 → アクメ  [×]  │
│    schema.org │                                  │  ─────────────      │
│    SKOS       │                                  │  出典・確信度         │
│              │                                  │                    │
├──────────────┴──────────────────────────────────┴────────────────────┤
│ 下部パネル（タブ）： SPARQL │ Turtle ビュー │ 検証結果 │ 履歴                │
└─────────────────────────────────────────────────────────────────────┘
```

### 7.2 主要な操作フロー

| 操作 | 手順 |
|---|---|
| ノード追加 | キャンバスの空白をダブルクリック → ラベル入力 → クラスをサジェストから選択 |
| エッジ追加 | ノードの縁からドラッグして別ノードへドロップ → プロパティ選択ポップアップ（定義域・値域から候補を絞り込み） |
| クラス定義 | 左ペインの「＋クラス」→ 名前入力 → 親クラスをドラッグで指定 |
| 語彙の再利用 | 左ペイン「外部語彙」から `schema:Person` をキャンバス／ツリーへドラッグ |
| テキスト編集 | 下部「Turtle ビュー」で直接編集 → 保存でグラフへ反映（構文エラーは行単位で表示） |
| 検証 | ヘッダの「検証」→ 違反ノードが赤枠でハイライト、右ペインに理由 |
| 推論 | ヘッダの「推論実行」→ 導出トリプルが点線エッジで表示。実線／点線はトグルで切替 |

### 7.3 UI をシンプルに保つためのルール

1. **既定では 1 画面 3 ペインのみ。** 高度な機能（推論設定、名前付きグラフ管理、IRI 編集）は「詳細」トグルの奥に置く。
2. **専門用語を画面に出さない。** 「クラス」→ 種類、「インスタンス」→ 項目、「プロパティ」→ 関係／属性、というラベル表記を既定にし、設定で専門用語表記に切替可能。
3. **エラーは常に修正候補とセットで示す。** 「値域違反です」ではなく「この関係の相手は『組織』である必要があります。〈アクメ〉を組織にしますか？」。
4. **ノード数が閾値（既定 500）を超えたら自動で近傍表示モードへ。** 全体表示は俯瞰用の別ビューに逃がす（NFR-04）。

## 8. API 仕様（抜粋）

すべて `/api/v1` 配下。認証は §13 参照。

| Method | パス | 説明 |
|---|---|---|
| `GET` | `/entities?q=&type=&limit=&offset=` | ラベル全文検索。JSON-LD 配列を返す |
| `POST` | `/entities` | インスタンス作成。`{label, types, properties}` を受け IRI を採番して返す |
| `GET` | `/entities/{iri}` | CBD を JSON-LD で返す。`?depth=` で近傍展開 |
| `PATCH` | `/entities/{iri}` | 差分更新。追加／削除するトリプルを指定 |
| `DELETE` | `/entities/{iri}` | 当該ノードと関連トリプルを削除 |
| `GET` | `/ontology` | クラス階層・プロパティ一覧をツリー構造の JSON で返す |
| `POST` | `/ontology/classes` / `/properties` | 語彙定義の追加 |
| `GET/POST` | `/sparql` | SPARQL 1.1 Protocol 準拠。`SELECT/CONSTRUCT/ASK/DESCRIBE` |

| `GET` | `/events` | SSE。他クライアントの変更をプッシュ |

## 9. MCP サーバー仕様

> **本サーバーは完全な読み取り専用である。** 更新系ツールを実装しないだけでなく、MCP プロセスは RDF ストアを **read-only ハンドルで開く**。アプリ層のフラグではなくストア層で権限を落とすため、実装ミスによる書き込みが原理的に起こらない。

### 9.1 提供形態

| トランスポート | 用途 | 起動 |
|---|---|---|
| **Streamable HTTP** | 常駐コンテナに対し AI クライアントが接続 | `http://localhost:8080/mcp` |
| **stdio** | ローカルクライアントがコンテナを都度起動 | `docker run -i --rm -v ./data:/data ontoforge mcp-stdio` |

### 9.2 Tools

すべて参照系。書き込み系ツールは存在しない。

| ツール名 | 入力 | 出力 |
|---|---|---|
| `search_entities` | `query`, `type?`, `limit?` | 該当ノードの IRI・ラベル・型・要約 |
| `get_entity` | `iri`, `depth?` | CBD を Turtle で返す（LLM が読みやすい形） |
| `list_classes` | `root?` | クラス階層のツリー |
| `list_properties` | `domain?` | プロパティ一覧（定義域・値域つき） |
| `describe_ontology` | — | オントロジー全体の自然言語サマリ＋主要クラス統計 |
| `get_neighbors` | `iri`, `depth`, `max_nodes` | 近傍サブグラフ |
| `find_path` | `from_iri`, `to_iri`, `max_hops` | ノード間の最短経路 |
| `sparql_select` | `query` | 結果テーブル。`SELECT / ASK / CONSTRUCT / DESCRIBE` のみ。`INSERT / DELETE / LOAD / CLEAR / DROP` はパース段階で拒否 |
| `validate_graph` | `shape?` | SHACL 検証結果 |
| `explain_inference` | `triple` | 導出トリプルの根拠（適用ルールと前提トリプル） |

### 9.3 Resources

| URI | 内容 |
|---|---|
| `ontoforge://ontology/schema.ttl` | 現在のオントロジー全体（Turtle） |
| `ontoforge://ontology/summary.md` | クラス・プロパティの説明を自然言語化したもの |
| `ontoforge://graphs` | 名前付きグラフ一覧と統計 |
| `ontoforge://examples/queries.md` | 本 KG に対する SPARQL の例文集 |

### 9.4 Prompts

| 名前 | 用途 |
|---|---|
| `explore_entity` | 特定エンティティを起点に KG を探索するための定型手順 |
| `build_sparql` | 自然言語の質問から本 KG のスキーマに沿った SPARQL を組み立てる |
| `extract_to_kg` | 与えられた文書から、本オントロジーに準拠したトリプル候補を Turtle で**出力させる**。KG へは書き込まれないので、利用者が内容を確認のうえ UI の Turtle ビューに貼り付けて取り込む |

### 9.5 AI が扱いやすくするための設計

- **スキーマを先に渡す。** `describe_ontology` は「どのクラスに何件のインスタンスがあり、どのプロパティで繋がるか」を自然言語＋簡略 Turtle で返し、LLM が当てずっぽうの SPARQL を書くのを防ぐ。
- **出力は Turtle を既定にする。** JSON-LD よりトークン効率と可読性で優る。
- **結果件数に上限を設ける。** 既定 100 件、`sparql_select` は結果サイズ上限とタイムアウト（既定 10 秒）を強制。
- **IRI にはラベルを併記して返す。** LLM が IRI だけを見て文脈を失わないようにする。

## 10. 推論・検証

### 10.1 推論

> **方針：「機械的に取ってこれる範囲」に限定する。** 記述論理の充足可能性判定を伴う OWL DL 推論（HermiT / ELK 等）は行わない。前向き連鎖のルール適用だけで有限回で停止する範囲に絞ることで、外部推論器・別コンテナ・長時間バッチのいずれも不要になる。

- 方式：**materialization（事前計算・前向き連鎖）**。実行時推論は行わず、`urn:ontoforge:inferred` に導出結果を書き出す。SPARQL 実行時のコストを増やさないため。
- プロファイル：

| 設定値 | 適用ルール | 用途 |
|---|---|---|
| `none` | 推論なし | 素の入力だけを見たいとき |
| `rdfs`（既定） | `rdfs:subClassOf` / `rdfs:subPropertyOf` の推移閉包、`rdfs:domain` / `rdfs:range` からの型付与 | 「社員は人物でもある」程度が自動で効けばよい通常運用 |
| `rl-lite` | 上記＋ `owl:inverseOf`、`owl:TransitiveProperty`、`owl:SymmetricProperty`、`owl:equivalentClass` / `equivalentProperty`、`owl:sameAs`（等値の伝播） | 逆向きの関係（所属 ⇄ 所属員）や推移的関係（部分の部分）を自動で埋めたいとき |

- **やらないこと**：クラス式（`owl:intersectionOf` 等）からの分類推論、カーディナリティ制約からの矛盾検出、`owl:disjointWith` の充足可能性判定。これらが必要な検証は SHACL（§10.2）で代替する。
- 停止性：ルールセットは有限で単調増加のため、固定点に達した時点で停止する。安全のため最大反復回数（既定 20）と導出上限を設ける。
- 説明可能性：各導出トリプルに「適用ルール名 + 前提トリプル」を保持し、UI と MCP（`explain_inference`）から参照できる。
- トリガ：手動実行、または「編集停止から N 秒後に自動」（設定可）。
- 表示：導出トリプルは点線エッジ＋淡色で描画し、編集不可とする。「なぜこの推論が出たか」の根拠トリプルをホバーで表示。

### 10.2 検証

- SHACL シェイプは UI から生成できる（「このクラスには必ずこの属性が必要」等をフォームで指定 → 裏で SHACL を出力）。
- 検証タイミング：保存時（軽量チェック）＋手動フル検証。
- 結果は `sh:ValidationReport` として保持し、違反ノードをキャンバス上で赤枠表示。

## 11. 入出力

| 種別 | 対応形式 |
|---|---|
| インポート | Turtle, TriG, N-Triples, N-Quads, RDF/XML, JSON-LD, CSV/TSV（列 → プロパティのマッピング UI 付き） |
| エクスポート | 上記 RDF 各形式に加え、GraphML（Gephi/yEd 用）、CSV ノード表＋エッジ表（Neo4j 用）、Mermaid（ドキュメント貼付用） |
| 語彙プリセット（同梱） | schema.org, SKOS, FOAF, Dublin Core Terms, PROV-O, OWL/RDFS |

CSV インポートのマッピングは「1 行 = 1 インスタンス、指定列 = IRI キー、他列 = プロパティ」を基本とし、マッピング定義自体を保存・再利用できるようにする。

## 13. セキュリティ

| 項目 | 方針 |
|---|---|
| 待受 | 既定で `127.0.0.1` のみにバインド。LAN 公開は明示的な設定を要する |
| 認証 | 既定なし（個人・ローカル単独利用のため）。`ONTOFORGE_AUTH_TOKEN` 設定時のみ Bearer トークン必須 |
| SPARQL 注入 | ユーザー入力はパラメータ化して埋め込む。生クエリ実行は専用エンドポイントに限定 |
| MCP 権限 | 参照のみ。更新系ツールを実装せず、ストアを read-only ハンドルで開き、SPARQL は AST を検査して更新句を拒否する（三重の防御、P4） |
| リソース枯渇 | クエリタイムアウト、結果件数上限、インポートファイルサイズ上限を強制 |
| 外部語彙取得 | 実行時に外部 URL を自動フェッチしない。取得は明示操作時のみ、ドメイン許可リスト付き |
| コンテナ | 非 root ユーザーで実行。読み取り専用ルートファイルシステム＋`/data` のみ書き込み可 |
